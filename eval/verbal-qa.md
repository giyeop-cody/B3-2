# B3-2 동료평가 대비 가이드

## 1. 이 과제가 뭔가요?
sorted()를 쓰지 말고 정렬 알고리즘을 직접 구현하여 파일 변경을 추적하는 mini-git 프로그램.

## 2. 평가 예상 질문

### 학습 목표 #1: Git의 내부 동작 (커밋 체인, 브랜치 포인터)

Q1. Git의 커밋 체인과 브랜치 포인터를 어떻게 구현했나요?
A. 각 커밋은 고유 해시(sha256)를 가지고, 부모 커밋의 해시를 참조합니다. 이렇게 커밋들이 부모→자식으로 연결되어 체인을 형성합니다. 브랜치는 단순히 "현재 커밋을 가리키는 포인터"입니다 — Git의 브랜치는 폴더가 아니라 포인터 하나입니다. checkout은 이 포인터를 다른 커밋으로 옮기는 것입니다. 코드에서는 `commit_map`(해시→커밋 객체)과 `HEAD` 포인터로 이를 구현했습니다.

### 학습 목표 #2: 그래프 자료구조로 커밋 히스토리 표현

Q2. 커밋 히스토리를 그래프로 어떻게 표현했나요?
A. `CommitGraph` 클래스가 커밋들을 노드로, 부모-자식 관계를 엣지로 하는 그래프를 만듭니다. 이 그래프로 세 가지를 할 수 있습니다:
1. **위상 정렬** (`topological_sort`): 부모가 자식보다 먼저 오도록 커밋을 정렬 → `log` 명령에서 사용
2. **최단 경로** (`find_shortest_path`): 두 커밋 간의 공통 조상을 찾을 때 BFS 사용
3. **조상 탐색** (`get_ancestors`): 특정 커밋의 모든 부모 커밋을 추적

### 학습 목표 #3: 정렬 알고리즘 직접 구현 (sorted() 금지)

Q3. 어떤 정렬 알고리즘을 구현했나요? 왜 그것을 선택했나요?
A. **병합 정렬(merge sort)**을 구현했습니다. O(n log n) 시간 복잡도로, O(n²)인 버블 정렬보다 훨씬 빠릅니다. 병합 정렬을 선택한 이유는:
1. 안정 정렬(stable sort) — 같은 키 값을 가진 원소의 순서가 보존됨
2. 최악의 경우도 O(n log n) 보장 — 퀵 정렬은 최악의 경우 O(n²)
3. 커밋을 타임스탬프나 작성자명으로 정렬할 때 일관된 결과

sorted() 없이 직접 구현한 이유는 정렬의 내부 원리(분할→정복→병합)를 체득하기 위함입니다.

### 학습 목표 #4: diff 알고리즘의 원리

Q4. diff 알고리즘을 어떻게 구현했나요?
A. **LCS(Longest Common Subsequence) 알고리즘**으로 줄 단위 파일 비교를 구현했습니다. `LcsDiff` 클래스가 두 파일을 줄 단위로 읽어서:
1. 각 줄을 배열의 원소로 취급
2. DP(동적 계획법) 테이블로 두 파일의 최장 공통 부분수열을 찾음
3. 공통이 아닌 줄은 "추가(+)"" 또는 "삭제(-)"로 표시

이것이 Git diff의 기본 원리입니다 — 파일 전체를 비교하는 게 아니라, 변경된 줄만 식별해서 보여줍니다.
